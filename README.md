# Mini NPU Simulator

패턴과 필터의 같은 위치 값을 곱하고 누적하는 MAC 연산을 구현한
Python 콘솔 프로그램입니다. 실제 NPU 하드웨어의 병렬 실행을 구현한
것은 아니며, AI 계산의 기초 원리를 반복문으로 재현합니다.

## 실행 방법

Python 3.8 이상과 표준 라이브러리만 사용합니다.
별도 패키지 설치는 필요하지 않습니다.

프로젝트 폴더에서 실행: python3 main.py

- 모드 1: 3×3 필터 A와 B를 각각 3줄 입력한 뒤 패턴을 3줄 입력합니다.
- 각 줄에는 숫자 3개를 공백으로 구분합니다.
- 모드 2: main.py와 같은 폴더의 data.json을 분석합니다.
- 파일 경로는 프로그램 파일 위치를 기준으로 하므로 실행 위치에 의존하지 않습니다.
- Ctrl+C 또는 EOF가 발생하면 안내 후 종료합니다.

## 파일 구성

| 파일 | 역할 |
|---|---|
| main.py | 모드 선택과 실행, 입력 중단 처리 |
| core.py | 배열 검증, 라벨 정규화, MAC 계산, epsilon 판정 |
| console.py | 행 단위 입력, 재입력 안내, 성능 측정 |
| analysis.py | JSON 로드, 케이스별 검증·판정·요약 |
| data.json | 과제 제공 필터와 패턴 원본 |
| logs/ | 실제 실행 및 오류 처리 검사 기록 |

## 구현 요약

배열은 리스트 안에 행 리스트를 넣은 2차원 구조입니다.
matrix[row][column]으로 특정 위치를 읽거나 변경할 수 있습니다.
행과 열 개수, 숫자 자료형, 유한한 값인지 검사합니다.
콘솔에서는 행마다 검증하고 잘못된 행만 다시 입력받습니다.
정확히 3개의 유효한 행을 모아 3×3 배열을 구성합니다.

MAC은 이중 반복문에서 total += pattern[r][c] * kernel[r][c]로 계산합니다.
mac 함수는 크기와 값이 사전 검증된 두 배열을 받습니다.
외부 배열을 전달할 때는 validate_matrix로 먼저 검증해야 합니다.
NumPy 등의 외부 라이브러리를 사용하지 않습니다.

expected의 '+'와 필터 키 'cross'는 Cross로,
'x'는 X로 정규화합니다. Cross와 X 표기도 허용합니다.
정규화 이후의 표준 라벨로 출력과 PASS/FAIL 비교를 수행합니다.
알 수 없는 라벨과 정규화 후 중복되는 필터 라벨은 오류로 처리합니다.

패턴 키 size_N_idx에서 N을 추출하여 size_N 필터를 선택합니다.
지원하는 JSON 크기는 5, 13, 25입니다.
패턴이나 필터의 크기가 맞지 않으면 해당 케이스를 FAIL로 기록합니다.
오류가 발생해도 나머지 케이스의 분석은 계속합니다.
최상위 스키마가 잘못되거나 파일을 읽을 수 없으면 분석 불가를 안내합니다.

동점 기준은 abs(score_a - score_b) < 1e-9입니다.
차이가 epsilon과 같거나 크면 더 높은 점수의 라벨을 선택합니다.
모드 1은 A/B 또는 판정 불가를 출력합니다.
모드 2는 Cross/X/UNDECIDED를 출력합니다.
UNDECIDED는 expected의 Cross 또는 X와 다르므로 FAIL입니다.

## 결과 리포트

### 실제 분석 결과와 실패 원인

1. 제공된 data.json의 6개 패턴을 분석한 결과 3개 PASS, 3개 FAIL입니다.
2. 실패 케이스는 size_5_1, size_13_2, size_25_1입니다.
3. size_5_1은 두 점수가 약 0.9로 같아 UNDECIDED이며 expected는 X입니다.
4. size_13_2는 두 점수가 약 7.5로 같아 UNDECIDED이며 expected는 Cross입니다.
5. size_25_1은 두 점수가 약 4.9로 같아 UNDECIDED이며 expected는 X입니다.
6. 이 세 패턴은 두 필터에 대한 MAC 점수만으로 라벨을 구분할 수 없습니다.
7. 이는 제공 라벨과 현재 점수·동점 정책 사이의 불일치이며 스키마 오류와 구별됩니다.
8. 라벨 정규화는 '+'와 Cross처럼 표기가 달라 발생하는 잘못된 FAIL을 방지합니다.
9. 그러나 정규화만으로 같은 점수를 가진 패턴의 동점을 해결할 수는 없습니다.
10. 부동소수점에서는 7.4999999999999973과 7.5처럼 작은 차이가 발생합니다.
11. 단순 대소 비교는 이런 작은 오차만으로 승자를 정할 수 있으므로 epsilon을 적용합니다.
12. epsilon은 계산값 자체를 고치는 것이 아니라 비교 시 동점으로 취급할 범위를 정합니다.
13. expected를 보고 승자를 선택하거나 원본 데이터를 수정하여 PASS 수를 늘리지 않았습니다.
14. 데이터/스키마 문제는 키, 필수 필드, 크기, 값, 라벨 검증으로 진단합니다.
15. 로직 문제는 3×3 십자가의 5점과 교차 점수 1점 등 알려진 결과로 검사합니다.
16. 수치 비교 문제는 거의 같은 점수와 epsilon 경계값을 별도로 검사합니다.
17. 의도적 오류 검사에서는 크기·라벨·키 오류 3개를 FAIL로 기록하고 다음 정상 케이스를 처리했습니다.
18. 제공 데이터의 FAIL과 검사 코드 자체의 통과 여부는 서로 다른 의미입니다.

### 성능 측정 결과

아래 값은 제공 데이터 분석 실행에서 얻은 실제 측정값입니다.
3×3은 예제 십자가를, 나머지는 해당 크기의 Cross 필터를
입력과 필터로 사용했습니다. 크기별 입력 내용은 동일하지 않습니다.

| 크기 | MAC 1회 평균 시간(ms) | MAC 횟수 N² |
|---|---:|---:|
| 3×3 | 0.002240 | 9 |
| 5×5 | 0.003061 | 25 |
| 13×13 | 0.011342 | 169 |
| 25×25 | 0.037428 | 625 |

배열 검증과 준비 후 1회 예열하고, 크기별 10회 반복 평균을 계산했습니다.
perf_counter로 MAC 함수 호출 구간을 측정했습니다.
입력·출력·파일 읽기·배열 검증은 측정에서 제외했습니다.
함수 호출, 결과의 유한성 검사와 시간 측정 자체의 부담은 포함됩니다.
표는 필터 하나의 MAC 호출 시간이며 두 필터 판정 전체 시간과 다릅니다.

### 시간 복잡도와 한계

바깥 반복문이 N번, 안쪽 반복문이 매번 N번 실행되어 총 N²번 누적합니다.
한 필터에 대해 곱셈 N²회와 누적 덧셈 N²회를 수행합니다.
표의 N²는 이 곱셈·누적 쌍의 횟수이며 개별 산술 연산 수는 약 2N²입니다.
필터 두 개를 비교하면 2N²개의 MAC을 수행하지만 시간 복잡도는 O(N²)입니다.
25×25는 3×3보다 MAC 횟수가 약 69.4배이며 측정 시간은 약 16.7배입니다.
시간 비율이 연산 횟수 비율과 정확히 같지 않은 이유는 고정 호출 비용,
타이머 부담, 시스템 상태와 작은 입력에서의 측정 변동 등이 있기 때문입니다.
이번 측정에서는 크기가 커질수록 평균 시간도 증가했습니다.
O(N²)의 근거는 반복문 구조이며 측정값은 그 증가 경향을 보여 줍니다.
입력과 필터의 저장 공간은 O(N²), MAC의 추가 작업 공간은 O(1)입니다.
실제 NPU의 병렬 처리 속도나 대형 AI 모델의 성능을 이 결과로 추정하지 않습니다.

## 설계 보완 설명

### normalize_label을 별도 함수로 분리한 이유

expected와 필터 키는 같은 의미를 서로 다른 표기로 표현합니다.
이를 읽는 곳마다 변환 코드를 작성하면 매핑이 달라지거나 누락될 수 있습니다.
normalize_label 함수에 변환 규칙을 모아 두면 필터와 expected에 같은 정책을
적용할 수 있고, 표기 추가와 오류 메시지 수정도 한 곳에서 수행할 수 있습니다.
정규화 함수만 독립적으로 검사할 수 있어 재사용성과 유지보수성도 높아집니다.
앞뒤 공백은 제거하고 대소문자를 구분하지 않으므로
' Cross ', 'CROSS', '+'는 Cross, ' x ', 'X'는 X가 됩니다.
알 수 없는 표기는 추측하지 않고 오류로 처리합니다.

### 새 라벨 추가 절차

현재 프로그램은 Cross와 X 두 라벨을 비교하도록 구현되어 있습니다.
새 라벨을 실제 지원하려면 다음 순서로 확장해야 합니다.

1. core.py의 normalize_label 매핑에 새 표기와 표준 라벨을 추가합니다.
2. data.json의 각 크기별 filters에 새 라벨의 필터를 추가합니다.
3. patterns의 expected에 사용할 새 표준 라벨과 허용 표기를 정의합니다.
4. analysis.py의 load_filters가 검사하는 필수 라벨 집합을 수정합니다.
5. 두 점수 전용 decide를 여러 라벨 점수 중 최댓값을 선택하도록 확장합니다.
6. 최상위 두 점수의 차이가 epsilon 미만이면 UNDECIDED로 처리합니다.
7. analysis.py의 계산·출력과 성능 측정을 새 필터 수에 맞게 수정합니다.
8. 새 라벨 정답, 기존 라벨, 동점, 알 수 없는 라벨, 중복 라벨을 검사합니다.
9. 전체 테스트 수와 PASS/FAIL 합계가 일치하는지 확인합니다.

매핑만 추가하면 다중 라벨 분류가 완성되는 것은 아닙니다.
위 내용은 확장 절차이며 현재 구현은 두 라벨 분류입니다.

### 새 크기 추가 절차

예를 들어 9×9를 추가하려면 data.json에 size_9 필터와
size_9_idx 패턴을 추가하고 각 배열을 9×9로 구성합니다.
analysis.py의 필터 로드, 지원 크기 검사, 성능 표 구성에 사용한
(5, 13, 25) 목록을 모두 갱신합니다.
정상 크기와 행·열 불일치 사례를 함께 검사합니다.

### CPU와 NPU의 계산 방식 및 병목

현재 Python MAC 함수는 CPU에서 이중 반복문을 순서대로 실행합니다.
각 위치에서 값을 읽고 곱한 다음 하나의 total에 차례로 누적합니다.
Python 반복문과 인덱싱 비용, 순차적인 누적 의존성이 병목이 될 수 있습니다.
데이터가 커지면 메모리에서 값을 가져오는 대역폭과 캐시 효율도 중요해집니다.

NPU는 다수의 MAC 연산 장치를 이용하여 여러 위치나 필터를 병렬로 처리합니다.
예를 들어 25×25 필터 하나는 625개의 MAC이 필요합니다.
현재 코드는 이를 순차 처리하지만 NPU는 작업을 여러 장치에 나누고
부분 합을 결합하는 방식으로 처리할 수 있습니다.
장치 수만큼 항상 빨라지는 것은 아니며 데이터 전송, 메모리 대역폭,
부분 합 결합, 장치 활용률 등이 실제 처리 속도를 제한합니다.

CPU 역시 SIMD, 여러 코어와 명령어 병렬성을 지원하므로
CPU 전체를 순수 직렬 장치라고 단정할 수는 없습니다.
여기서 직렬이라는 설명은 현재 Python 반복문 구현을 가리킵니다.
이 프로그램은 실제 NPU 실행 시간이나 병렬 가속률을 측정하지 않습니다.
